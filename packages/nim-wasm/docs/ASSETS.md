# The compiler assets: where they come from, and how to move them

`assets/nim/` holds the Nim compiler, compiled to WebAssembly. It is the one part of this package that is
not written here, so this file records what it is, where it came from, how it was built, and what to do
when it needs to be replaced.

## What the three files are

| File | Size | What it is |
| --- | --- | --- |
| `nim.wasm` | 4.59 MB | The Nim 2.2.4 compiler, compiled to wasm with Emscripten |
| `nim-bundle.js` | 6.26 MB | Its Emscripten loader, patched by the same project: it carries the standard library and writes submitted source into the compiler's memory filesystem |
| `nimbase.h` | 20 KB | The header Nim's generated C includes. The compiler does not ship it, so it is mounted into the clang filesystem as `include/nimbase.h` |

The first two are a matched pair: `nim-bundle.js` loads `nim.wasm` through `Module.locateFile` (a browser,
by URL) or `Module.wasmBinary` (Node, from these bytes). Replacing one without the other will not work.

## Where they come from

- **The language**: Nim **2.2.4**, MIT. <https://github.com/nim-lang/nim>
  The version is not taken on trust — the C the compiler emits is headed
  `/* Generated by the Nim Compiler v2.2.4 */`, which is how to check it.
- **The build**: the [Nim-WASM-Compiler](https://github.com/benagastov/Nim-WASM-Compiler) project, MIT —
  a third-party project that compiles Nim to wasm and publishes the result as a static site.
  Commit `ca3471ae124b40b51268da6e202753dfa061731c`, 2026-06-15, served from
  `https://benagastov.github.io/Nim-WASM-Compiler/static/nim/`.

The exact bytes are pinned by size and SHA-256 in [`src/asset-receipts.js`](../src/asset-receipts.js),
along with that provenance, and **every read verifies against the pin** — a host that serves something
else fails with both digests rather than running a different compiler. The assets are also committed, so
the package works if that host ever goes away.

`THIRD-PARTY-NOTICES.md` covers the licensing side of the same facts.

## How they were built

**Not here, and not by a command.** The upstream README gives this as the short version:

```bash
nim c --cpu:wasm32 --os:any --define:danger --passC:"-s USE_ZLIB=1"
```

— a host Nim compiling the compiler for `cpu:wasm32`, with Emscripten as the C compiler behind it. What
that leaves out is the part that makes the result usable in a browser, and which the shipped bundle
plainly carries:

1. **The standard library is embedded in the loader.** `nim-bundle.js` contains a `__libFiles` map of 337
   files — `/lib/system/jssys.nim` and friends — encoded as base64, unpacked into the compiler's memory
   filesystem at startup. The wasm compiler has no real filesystem, so without this it cannot `import`
   anything at all.
2. **The loader is patched to accept source.** A `__NIM_USER_CODE_PENDING__` global is written to
   `/tmp/user.nim` the first time the compiler touches that path, and `__NIM_USER_CODE__` decides whether
   the bundle auto-runs at load. Without this there is no way to hand the compiler a program.

So a faithful rebuild means owning a small build pipeline — Emscripten, a Nim checkout at the tag, the
compiler build, and those two patches — rather than running one command. This package does not attempt
it, and does not need to unless the assets must change for a reason of our own.

Two details of the upstream build it is worth knowing, because they are not ours to choose:
`-d:danger` is upstream's, which trades Nim's runtime checks for size — the compiler is a tool here, not
the user's program — and the Emscripten version is not documented upstream.

## How to move the pin

Replacing the assets is deliberate, and there is a script for it. From the repository root:

```bash
node scripts/fetch-nim-assets.mjs                # fetch what is missing, then verify everything
node scripts/fetch-nim-assets.mjs --verify-only   # verify only, no network
```

`--verify-only` is what to run after touching anything in `assets/nim/`, and it is safe to run in a
check. Neither mode ever writes the pin: an upstream that has moved, or a download that arrived
corrupted, stops there with the expected and the actual digest rather than quietly becoming the new
truth.

To move it on purpose:

1. Delete the files that need replacing from `assets/nim/`, then run the script *without* `--update`. It
   fetches them and compares against the current pin. If upstream has not moved, that succeeds and there
   is nothing to re-pin; if it fails, upstream is serving bytes this package was not pinned to — read what
   it says, and only then decide whether re-pinning is what you meant to do.
2. `node scripts/fetch-nim-assets.mjs --update` prints the receipts for the bytes that are now on disk.
   Paste them into `src/asset-receipts.js`, and update `ASSET_SOURCE` alongside them — commit, date, and
   the compiler version if that changed too. A pin without its provenance is only half the record.
3. Rebuild the IIFE bundle (`npm run build:iife`). The receipts are bundled into
   `dist/nim-wasm.global.js`, so it carries the old pin until it is rebuilt.
4. Run the tests — `npm test` in `packages/nim-wasm` and in the repository root — and then both targets
   in a browser (`browser-nim`'s page). What a stale or wrong compiler breaks first is `import`s and
   `echo`, which the suites cover, and the checks in the root README's sample set are the sharpest test
   of the compiler's runtime being intact.

## Things not to do

- **Do not re-pin by accepting whatever arrives.** Deleting the receipts and letting the first download
  define them is the difference between a pin and a receipt: it would adopt a moved upstream silently,
  which is the whole failure mode this pin exists to catch.
- **Do not edit `nim-bundle.js` by hand.** It is a 6 MB Emscripten build with the patches above already
  applied, and a change to it is a change nobody can reproduce from source.
